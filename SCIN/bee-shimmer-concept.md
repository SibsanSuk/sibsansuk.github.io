# Bee Shimmer: Risk-Aware UI as a Whole-Screen Warning

## แนวคิดย่อ

**Bee Shimmer** คือแนวคิดส่วนติดต่อผู้ใช้ที่สื่อสารความเสี่ยงผ่าน “พฤติกรรมร่วมกันของทั้งหน้าจอ” แทนการใช้ข้อความเตือน กล่อง dialog หรือสีของปุ่มเพียงองค์ประกอบเดียว เมื่อผู้ใช้กำลังเข้าใกล้การกระทำที่อาจมีความเสี่ยง เช่น เลื่อนเมาส์เข้าใกล้ปุ่ม Post องค์ประกอบต่าง ๆ บนหน้าเว็บจะค่อย ๆ เกิด shimmer เป็นระลอกคลื่นออกจากจุดที่กำลังจะกด

ชื่อ Bee Shimmer สื่อถึงสัญญาณเตือนแบบรวมหมู่ที่คล้ายฝูงผึ้ง แต่ละองค์ประกอบไม่ได้เตือนอย่างโดดเดี่ยว ทว่าช่วยกันเปลี่ยนบรรยากาศของ interface เพื่อทำให้ผู้ใช้รับรู้ว่า “บริบททั้งหมดกำลังตอบสนองต่อการตัดสินใจนี้”

## ปัญหาที่ต้องการศึกษา

คำเตือนความเสี่ยงใน UI โดยทั่วไปมักแยกออกจากบริบท เช่น toast, modal, tooltip หรือข้อความสีแดงใกล้ปุ่ม ผู้ใช้อาจมองข้ามคำเตือนเหล่านี้ เกิดความเคยชินกับการกดผ่าน หรือรู้สึกว่าคำเตือนขัดจังหวะงาน

Bee Shimmer เสนอวิธีเตือนแบบ ambient และ contextual โดยไม่หยุด flow ทันที แต่ค่อย ๆ เพิ่มความเด่นชัดตามความใกล้ของเจตนากระทำ เช่น ระยะห่างของ pointer จากปุ่ม ระยะเวลาที่ลังเล หรือระดับความเสี่ยงของเนื้อหา

## สมมติฐานหลักของการออกแบบ

1. การที่หลายองค์ประกอบตอบสนองพร้อมกันจะดึงความสนใจได้ดีกว่าการเปลี่ยนเฉพาะปุ่ม
2. สัญญาณเตือนที่ค่อย ๆ เพิ่มตามความใกล้ของการกระทำจะช่วยให้ผู้ใช้หยุดทบทวน โดยรบกวน flow น้อยกว่า modal
3. คลื่นที่มีจุดกำเนิดจาก action เป้าหมายจะช่วยให้ผู้ใช้เชื่อมโยงสัญญาณเตือนกับสาเหตุได้
4. สัญญาณที่แรงเกินไปหรือเกิดบ่อยเกินไปอาจสร้างความรำคาญ ความกังวล หรือทำให้เกิด warning fatigue

## รูปแบบปฏิสัมพันธ์ใน Prototype

สถานการณ์จำลองเป็นหน้า social network ที่มีช่องเขียนข้อความและปุ่ม Post

- **สถานะปกติ:** หน้าจออยู่นิ่งและมีความต่างสีตามปกติ
- **Approach:** เมื่อ pointer เริ่มเข้าใกล้ปุ่ม Post หน้าเว็บจะเพิ่มแสงสีอำพันอย่างค่อยเป็นค่อยไป
- **High proximity:** เมื่อเข้าใกล้มากขึ้น shimmer จะเคลื่อนผ่าน card, navigation, avatar และ feed เป็นระลอก โดยมีจุดกำเนิดสัมพันธ์กับตำแหน่งปุ่ม
- **Commit:** เมื่อกด Post ระบบจะชะลอการส่งชั่วครู่และแสดงจังหวะ “reflect” เพื่อสื่อสารว่านี่เป็นช่วงเวลาสำหรับตรวจทาน
- **Cancel:** เมื่อ pointer เคลื่อนออก ความเข้มของ effect จะลดลงอย่างนุ่มนวล โดยไม่ทิ้งสถานะค้าง

ต้นแบบนี้เป็นการสาธิต interaction เท่านั้น ยังไม่ได้วิเคราะห์ความเสี่ยงจากข้อความจริง

## โมเดลเชิงแนวคิด

ความเข้มของสัญญาณเตือนสามารถนิยามเบื้องต้นเป็น

```text
warning intensity = content risk × action proximity × interaction confidence
```

- `content risk` คือคะแนนความเสี่ยงจากเนื้อหา เช่น ข้อมูลส่วนบุคคล ความรุนแรง หรือความเป็นพิษ
- `action proximity` คือความใกล้ของการลงมือ เช่น pointer distance, focus หรือ touch-down
- `interaction confidence` คือความเชื่อมั่นว่าผู้ใช้กำลังจะทำ action จริง เช่น ความเร็วและทิศทางของ pointer

ใน prototype แรกใช้เฉพาะ `action proximity` เพื่อแยกศึกษาผลของ motion และ whole-screen participation ก่อน

## คำถามวิจัย

- Whole-screen shimmer ช่วยให้ผู้ใช้สังเกตคำเตือนได้มากกว่าการเตือนที่ปุ่มเพียงจุดเดียวหรือไม่
- effect ช่วยเพิ่มเวลาตรวจทานและลดโพสต์ที่ผู้ใช้ภายหลังเสียใจหรือไม่
- ระดับความเข้ม ความเร็ว และรัศมีแบบใดที่รับรู้ได้ แต่ไม่รบกวนหรือชักจูงเกินควร
- ผู้ใช้เข้าใจหรือไม่ว่า shimmer หมายถึง “มีความเสี่ยง” ไม่ใช่เพียง animation ตกแต่ง
- ผลลัพธ์แตกต่างกันอย่างไรระหว่าง mouse, keyboard, touch และผู้ใช้ที่ไวต่อ motion

## แนวทางการทดลอง

เปรียบเทียบอย่างน้อย 3 เงื่อนไข

1. **Control:** ไม่มีคำเตือน
2. **Local warning:** เตือนเฉพาะบริเวณปุ่ม Post
3. **Bee Shimmer:** UI และบริบททั้งหน้าจอร่วมกันแสดงคลื่นเตือน

ตัวแปรต้นอาจประกอบด้วยรูปแบบคำเตือน ระดับความเสี่ยง และความเข้มของ motion ส่วนตัวแปรตามอาจประกอบด้วยอัตราการสังเกต เวลาก่อนกด อัตราการแก้ไขข้อความ อัตราการยกเลิก ความเข้าใจ ความรำคาญ ภาระทางความคิด และความเชื่อมั่นต่อระบบ

ควรเก็บทั้งข้อมูลพฤติกรรมและการสัมภาษณ์หลังใช้งาน เพราะการหยุดนานขึ้นอาจหมายถึงการทบทวน หรืออาจหมายถึงผู้ใช้สับสนกับ effect ก็ได้

## หลักการออกแบบและข้อควรระวัง

- สัญญาณควรสัมพันธ์กับระดับความเสี่ยงและอธิบายเหตุผลได้
- ไม่ควรใช้ motion เป็นช่องทางเดียว ควรมีข้อความ ไอคอน หรือ feedback ที่รองรับผู้ใช้หลายกลุ่ม
- รองรับ `prefers-reduced-motion` และให้ผู้ใช้ลดหรือปิด animation ได้
- ต้องมี feedback สำหรับ keyboard focus และ touch ซึ่งไม่มีแนวคิด “pointer เข้าใกล้” แบบ mouse
- หลีกเลี่ยงการกระพริบถี่ ความต่างสีรุนแรง และ motion ที่อาจกระตุ้นอาการเวียนศีรษะหรือชัก
- ไม่ควรใช้ effect เพื่อขู่ ทำให้อับอาย หรือบังคับให้ผู้ใช้ทำตามการตัดสินใจของระบบ
- หากมี risk model จริง ต้องศึกษาความผิดพลาด อคติ false positive และช่องทางอุทธรณ์หรือดำเนินการต่อ
- งานทดลองเกี่ยวกับข้อความละเอียดอ่อนควรคำนึงถึงความเป็นส่วนตัว การเก็บ log และ informed consent

## ขอบเขตของต้นแบบรอบแรก

- หน้า social network จำลองแบบไฟล์ HTML เดียว
- ช่องเขียนข้อความและปุ่ม Post ใช้งานได้
- feed และข้อมูลรอบข้างใช้ skeleton เพื่อเน้นการศึกษาพฤติกรรมของ effect
- ความเข้มของ shimmer คำนวณจากระยะ pointer ถึงปุ่ม Post
- ทั้ง viewport มีคลื่นบรรยากาศ และแต่ละองค์ประกอบมี highlight ร่วมกัน
- มีสถานะ keyboard focus, touch/press และ reduced motion

## ขั้นต่อไป

1. ทำ pilot test เพื่อปรับรัศมี ความเร็ว และระดับความเข้ม
2. เพิ่มเงื่อนไข local warning เพื่อใช้เป็น baseline ในไฟล์เดียวกัน
3. สร้าง risk scenarios หลายระดับโดยยังไม่ใช้ข้อมูลจริงของผู้เข้าร่วม
4. เพิ่ม event logging เฉพาะข้อมูลที่จำเป็น เช่น approach time, dwell time, edit และ cancel
5. ทดสอบความเข้าใจของ metaphor ก่อนวัดประสิทธิผลของคำเตือน
