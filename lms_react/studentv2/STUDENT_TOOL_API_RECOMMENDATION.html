Target API Design

Recommended Unified API

แนวทางออกแบบ API กลางสำหรับ Student Learning Tools ให้ BookRoll, Video, Chatbot, VK และ Adaptive Quiz ไปในทิศทางเดียวกัน

สำหรับProduct, API Platform, Backend, Frontend และ QA
ขอบเขตStudent Dashboard v2 และ adapter ของเครื่องมือการเรียน
สถานะข้อเสนอสำหรับหารือและจัดทำ OpenAPI contract ต่อ
วันที่จัดทำ14 สิงหาคม 2026
แนวคิดหลัก
Browser เรียก API Gateway เพียงระบบเดียวด้วย OIDC Bearer token ส่วน Gateway รับผิดชอบการแปลง identifier, จัดการ secret, เรียก upstream และ normalize response ของทุกเครื่องมือให้อยู่ใน schema เดียวกัน

 

1. Recommendation summary

ปัญหาปัจจุบันไม่ใช่เพียงชื่อ endpoint ต่างกัน แต่รวมถึง identifier, authentication, response shape, ความหมายของ missing data และวิธีจัดการ error ที่ไม่เหมือนกัน ข้อเสนอคือเพิ่ม Learning Data Gateway เป็น contract กลาง โดยยังคง upstream เดิมไว้หลัง adapter ในช่วง migration

Target state: Frontend ส่งเพียง Bearer token และ course_id จากนั้นใช้ endpoint pattern และ JSON schema เดียวกันทุกเครื่องมือ ไม่ส่ง email, UUID หรือ API key ไปยัง tool service โดยตรง
  1. ใช้ OIDC sub เป็น learner identity หลัก และ resolve email ภายใน Gateway
  2. ใช้ stable course/activity ID จาก course structure เป็น canonical ID
  3. ใช้ path pattern เดียวกัน: /api/v1/me/courses/{course_id}/tools/{tool_type}/...
  4. ทุก response ใช้ common envelope, summary, activity และ error schema เดียวกัน
  5. ข้อมูลเฉพาะเครื่องมืออยู่ใน metrics โดยไม่ทำให้ field กลางเปลี่ยนความหมาย
  6. Gateway จัดการ upstream API key, CORS, timeout, retry, cache และ observability
  7. Overall progress คำนวณฝั่ง Backend พร้อมส่งสูตร, weights และ missing-data policy กลับมาอย่างโปร่งใส
  8. รองรับ partial response เพื่อให้ dashboard แสดงข้อมูลส่วนที่สำเร็จได้

3. API conventions กลาง

หัวข้อข้อกำหนดแนะนำ
Base URLhttps://learning-api.meca.in.th/api/v1 หรือ same-origin /api/v1
Student identityใช้ /me; Gateway resolve learner จาก token ห้ามรับ email/sub จาก query เพื่อเปลี่ยนผู้เรียน
Teacher identityใช้ endpoint แยก /learners/{learner_id} และตรวจ scope/assignment
JSON namingsnake_case ทั้ง request และ response
TimeTimestamp เป็น ISO 8601 UTC; duration เป็นจำนวนวินาทีและลงท้าย _seconds

VersioningMajor version ใน URL; additive fields ไม่เปลี่ยน version, breaking change ไป v2

กติกาของ common fields

  • summary ใช้ field เดียวกันทุก tool และต้องสอดคล้องกับ activities
  • activity_id มาจาก course structure และต้อง stable แม้เปลี่ยนชื่อหัวข้อ
  • metrics เก็บข้อมูลเฉพาะ tool แต่ห้ามใช้แทน field กลาง
  • partial=true หมายถึง response ใช้งานได้บางส่วนและต้องอ่าน warnings/status ราย tool
  • Gateway ไม่ส่ง raw upstream payload เป็นค่า default; debug payload ต้องอยู่ใน environment/permission ที่จำกัด

6. Recommended API รายเครื่องมือ

6.1 BookRoll

Common progress  •  Page metrics  •  Stable activity ID

GET /api/v1/me/courses/{course_id}/tools/bookroll/progress

Gateway ใช้ token หา learner identity แล้วเรียก BookRoll adapter โดยไม่ให้ browser ส่ง userID หรือ timestamp cache-busting เอง

"metrics": {
  "pages_read": 7,
  "pages_total": 10,
  "reading_sessions": 3,
  "active_seconds": 820
}
  • progress_percent คำนวณจาก pages_read/pages_total ที่ Gateway
  • ถ้ารู้ว่าเอกสารมี 10 หน้าและผู้เรียนยังไม่อ่าน ให้ส่ง 0 ไม่ใช่ null
  • ห้าม dedupe ด้วยชื่อ; mapping ต้องใช้ canonical activity ID

6.2 Video

Common progress  •  Timeline optional  •  Seconds

GET /api/v1/me/courses/{course_id}/tools/video/progress?include=timeline
"metrics": {
  "watched_seconds": 510,
  "duration_seconds": 600,
  "watch_sessions": 4,
  "timeline": [
    { "start_seconds": 0, "end_seconds": 120, "view_count": 2 },
    { "start_seconds": 120, "end_seconds": 240, "view_count": 1 }
  ]
}
  • รวม bar และ heatmap ให้อยู่ใน activity เดียว ไม่บังคับ frontend join response
  • Timeline เป็น optional include เพื่อลด payload
  • ใช้วินาทีแทน label เวลาเพื่อให้คำนวณและวาดผลได้สม่ำเสมอ

6.3 Chatbot

Quiz schema  •  Attempts  •  Peer comparison optional

GET /api/v1/me/courses/{course_id}/tools/chatbot/progress?include=peer_comparison
"metrics": {
  "quiz_role": "posttest",
  "attempts": 2,
  "best_score": { "correct": 8, "total": 10, "percent": 80 },
  "latest_score": { "correct": 7, "total": 10, "percent": 70 },
  "average_attempt_seconds": 185,
  "peer_comparison": {
    "cohort_average_percent": 64,
    "learner_percentile": 78,
    "learners_attempted": 120
  }
}
  • Gateway ซ่อนการ fallback ระหว่าง Profile API และ SBS legacy
  • Response บอก source_quality ใน meta ได้ เช่น primary หรือ legacy_fallback
  • ใช้ Quiz schema เดียวกับ Adaptive Quiz เพื่อลด logic ใน frontend

6.4 VK

Activity metrics  •  Normalized units  •  No N+1 for client

GET /api/v1/me/courses/{course_id}/tools/vk/progress?chapter_id={chapter_id}
"metrics": {
  "active_seconds": 940,
  "coding_score_percent": 75,
  "solution_score_percent": 80,
  "coding_seconds": 520,
  "capture_seconds": 80,
  "annotate_seconds": 120,
  "training_seconds": 220,
  "objects_used": 5,
  "images_used": 12,
  "snap_count": 4,
  "switch_count": 3,
  "skill_result": "developing"
}
  • แปลงชื่อ metric ที่มี space/case ต่างกันเป็น snake_case ที่ stable
  • แปลงเวลาเป็นวินาทีและคะแนนเป็น 0–100 ก่อนส่ง client
  • Gateway จัดการ course/chapter fan-out, cache และ concurrency; browser เรียกครั้งเดียว

6.5 Adaptive Quiz

Quiz schema  •  Server-side key  •  Collection metadata

GET /api/v1/me/courses/{course_id}/tools/adaptive_quiz/progress?include=peer_comparison
"metrics": {
  "collection_id": "collection-01",
  "collection_title": "แบบฝึกหัดบทที่ 1",
  "quiz_role": "practice",
  "attempts": 3,
  "best_score": { "correct": 9, "total": 10, "percent": 90 },
  "latest_score": { "correct": 8, "total": 10, "percent": 80 },
  "completion_percent": 100
}
  • API key อยู่ที่ Gateway เท่านั้น
  • ref_code และ lead_label resolve จาก canonical course/activity mapping
  • ใช้ common Quiz schema เดียวกับ Chatbot

7. Aggregate Dashboard API

GET /api/v1/me/courses/{course_id}/dashboard
  ?include=structure,activities,timeline,peer_comparison

Endpoint นี้เหมาะกับ Student Dashboard เพราะลดจำนวน browser requests และทำให้ Gateway กำหนด timeout/partial response ได้จากจุดเดียว

Partial response policy

  • Auth, invalid course หรือ permission failure: ตอบ 4xx และไม่มี dashboard data
  • Tool ใดล้มเหลว: ตอบ 200 พร้อม meta.partial=true, availability และ warning ราย tool
  • ทุก tool ล้มเหลว: ตอบ 503 พร้อม error envelope
  • Frontend แสดงข้อมูลที่สำเร็จและปุ่ม retry โดยส่ง request เดิมหรือเรียก tool endpoint เฉพาะตัว

8. Overall progress policy

ไม่ควรซ่อนสูตรไว้ใน frontend: Backend ควรส่งทั้งค่าที่คำนวณแล้วและ metadata ของสูตร เพื่อให้ Product, QA และ Analytics ตีความตรงกัน
กรณีนโยบายแนะนำ
Activity อยู่ใน course แต่ผู้เรียนยังไม่เริ่มนับ progress = 0
Tool ไม่ได้ configure ใน courseไม่รวมในตัวหาร และระบุ not_configured
Upstream ล่ม/timeoutห้ามตีความเป็น 0; ให้ค่า null, partial=true และ exclude ชั่วคราว
Tool ไม่มี metric ที่แปลงเป็น progress ได้กำหนด scoring rule ใน course configuration หรือไม่รวมพร้อม reason
Weightsอ่านจาก versioned course configuration; ถ้าไม่มีให้ใช้ค่า default ที่ประกาศชัดเจน

แนวทาง migration: ระยะแรกคงสูตร BookRoll + Video เพื่อไม่ให้ตัวเลขเปลี่ยนทันที แต่ย้ายสูตรไป Backend และส่ง calculation metadata จากนั้นจึงทดลองรวม Chatbot, VK และ Adaptive Quiz ผ่าน versioned policy

9. Security และ reliability baseline

หัวข้อข้อกำหนดขั้นต่ำ
Secretsเก็บ upstream key ใน secret manager; ห้ามฝังใน JS, HTML หรือ mobile bundle
Authorization/me ใช้ token subject; teacher route ตรวจ role, assignment และ course scope
PIIไม่ log token/email เต็ม; mask identifier และกำหนด retention
Timeoutกำหนดต่อ adapter เช่น connect/read/total timeout และคืน retryable status
RetryRetry เฉพาะ GET ที่ safe พร้อม exponential backoff + jitter และจำกัดจำนวนครั้ง
CacheCourse structure cache นานกว่า learner progress; รองรับ ETag และ short TTL
Rate limitจำกัดตาม learner/client และป้องกัน fan-out amplification
ObservabilityRequest ID เดียวตลอด gateway → adapter → upstream พร้อม latency/status ราย tool
Contract testsJSON Schema/OpenAPI tests สำหรับ common fields และ fixture ต่อ adapter

11. Migration plan

Phase 0 — Contract decisions
ยืนยัน canonical IDs, progress policy, tool enums และ error model

Phase 1 — Gateway skeleton
OIDC validation, request ID, common envelope, Course adapter และ OpenAPI

Phase 2 — Read adapters
BookRoll + Video ก่อน เพราะใช้คำนวณ overall ปัจจุบัน พร้อม contract tests

Phase 3 — Quiz adapters
Chatbot primary/legacy และ Adaptive Quiz บน common Quiz schema พร้อมย้าย secret

Phase 4 — VK adapter
Server-side fan-out, cache, normalized metrics และ concurrency control

Phase 5 — Aggregate endpoint
Dashboard partial response, timeout policy และ ETag

Phase 6 — Frontend cutover
เปิด feature flag, compare old/new payload, shadow traffic และ rollback path

Phase 7 — Policy evolution
ทดลอง overall weights ใหม่ด้วย versioned configuration และ analytics validation

Definition of done

☐ มี OpenAPI 3.x และ JSON Schema ของ common response/error

☐ ทุก adapter ผ่าน contract fixtures ทั้ง success, no activity, missing mapping, timeout และ malformed upstream

☐ Browser ไม่มี upstream API key และไม่เรียก third-party learning service โดยตรง

☐ Stable activity ID จับคู่ course structure ได้ทุก tool

☐ Dashboard แยก not_started, not_configured และ upstream_unavailable ได้ชัดเจน

☐ Overall progress ส่ง method, included tools, weights source และ missing-data policy

☐ มี request tracing และ dashboard latency/error rate ราย adapter

☐ มี feature flag, payload comparison และ rollback plan ก่อน cutover

12. Decisions ที่ต้องยืนยันก่อนเขียน OpenAPI

  1. Canonical activity ID จะใช้ Open edX block ID โดยตรง หรือสร้าง Learning Activity Registry ID
  2. Default overall progress policy และ weights ของแต่ละ tool
  3. ข้อมูล peer comparison ใดอนุญาตให้ Student เห็นได้
  4. Teacher API ใช้ learner ID แบบใด และตรวจ scope ผ่าน assignment ใด
  5. Latency budget ของ aggregate endpoint และ timeout ต่อ adapter
  6. Retention/caching policy ของ learner progress และ raw upstream data
